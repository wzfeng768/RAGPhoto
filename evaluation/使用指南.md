## 系统概述

### 评估模式

本系统对比三种问答方法：

1. **Agentic RAG + 知识图谱**: 完整的Agent RAG系统（向量检索 + 知识图谱增强）
2. **Agentic RAG（纯向量）**: 仅使用向量检索的Agent RAG系统
3. **Direct LLM**: 直接使用大模型回答（无检索）

### 核心特性

✅ **双重评估体系**:
- **RAGAS指标**: 评估表述质量和检索效果
- **事实正确性**: 评估答案的事实准确性（**优先级更高**）

✅ **加权综合评分**:
- 事实正确性权重: **70%**（优先）
- RAGAS指标权重: **30%**（辅助）
- 公式: `weighted_score = fact_correctness × 0.7 + ragas_avg × 0.3`

✅ **一票否决机制**:
- 如果答案包含关键事实错误，即使表述再好，最高只能得0.3分
- 确保事实错误的答案不会获得高分

✅ **增量评估机制** ⭐新功能:
- **实时保存**: 每完成一个问题立即保存结果
- **断点续传**: 中途中断可从上次位置继续
- **自动重试**: 检测到NaN指标自动重试（最多3次）
- **详细日志**: 每个问题的评估过程都有详细输出
- **防止丢失**: 不再担心长时间评估中途失败导致数据丢失

## 评估指标说明

### RAGAS指标（6个）

所有模式都会计算全部6个RAGAS指标：

| 指标 | 含义 | Direct LLM模式 |
|------|------|----------------|
| **faithfulness** | 答案对检索内容的忠实度 | 0（无检索上下文） |
| **answer_relevancy** | 答案与问题的相关性 | ✓ 正常计算 |
| **context_precision** | 检索上下文的精确度 | 0（无检索上下文） |
| **context_recall** | 上下文召回率 | 0（无检索上下文） |
| **answer_correctness** | 答案与标准答案的正确性 | ✓ 正常计算 |
| **answer_similarity** | 答案与标准答案的语义相似度 | ✓ 正常计算 |

### 事实正确性指标（7个）

**核心指标：`factual_correctness`** (0-1)
- 综合评分，考虑覆盖率和准确性
- 如有关键错误，触发一票否决（≤0.3）
- **智能数值评估** ⭐新特性：理解语义上等价的数值表达

**辅助指标：**
1. **`key_facts_coverage`**: 标准答案中关键事实的覆盖率
2. **`fact_accuracy`**: 事实准确性（扣除错误惩罚后）
3. **`fact_precision`**: 生成答案中正确事实的比例
4. **`fact_recall`**: 召回标准答案中的事实
5. **`hallucination_rate`**: 幻觉率（生成但无支持的事实）
6. **`context_supported_rate`**: 上下文支持率
7. **`critical_errors`**: 关键错误数量

**数值语义等价性识别** ⭐改进:

系统现在能够智能识别语义上等价的数值表达，避免过于严格的字面匹配：

| 标准答案 | 认为正确的回答示例 |
|---------|-------------------|
| 98%-99% | 接近100%、约100%、nearly 100%、approximately 100% |
| 50% | 约50%、around 50%、大约一半、about half |
| 10-15% | 大约10-15%、roughly 10-15%、approximately 10-15% |
| 1000-1500 | 约1000-1500、around 1000-1500、大约1000多 |

**评估原则：**
- ✅ 重视语义意义而非精确措辞
- ✅ 对于1-2%以内的偏差，如果使用"约"、"接近"等词，视为正确
- ✅ 数值范围重叠或相邻则视为兼容
- ✅ 理解中英文的近似表达（如"接近"、"approximately"、"around"等）

### 加权综合评分

**`weighted_score`**: 最终推荐使用的评分

```
weighted_score = factual_correctness × 0.7 + ragas_average × 0.3
```

**评分等级：**
- **0.8-1.0**: 优秀 - 事实正确且表述良好
- **0.6-0.8**: 良好 - 轻微问题但总体准确
- **0.4-0.6**: 一般 - 存在明显事实问题
- **0.0-0.4**: 较差 - 关键错误或大部分不正确

### 4. 增量评估与断点续传 ⭐新功能

**增量评估**（默认启用）：每完成一个问题就立即保存，不再需要等待全部完成。

#### 基本使用

```bash
# 标准评估（自动启用增量保存）
python evaluate_rag.py --dataset computational --num_questions 50

# 如果评估中途中断（网络、API限额等），使用 --resume 继续
python evaluate_rag.py --dataset computational --num_questions 50 --resume

# 使用批量模式（关闭增量保存，全部完成后一次性保存）
python evaluate_rag.py --dataset computational --num_questions 10 --no-incremental

# 跳过不稳定的RAGAS评估（只使用事实检查）⚠️推荐
python evaluate_rag.py --dataset computational --num_questions 10 --skip-ragas

# 组合使用：自定义模型 + 跳过RAGAS + 断点续传
python evaluate_rag.py \
  --dataset all \
  --num_questions 50 \
  --answer-model gpt-4o-mini \
  --eval-model gpt-4o-mini \
  --skip-ragas \
  --resume
```

## 常见问题

### Q0: RAGAS评估超时或出错，怎么办？ ⚠️ 常见问题

**症状**：
- 出现 `TimeoutError` 或 `IndexError: list index out of range`
- 程序在 "Computing RAGAS metrics..." 时卡住
- 出现 `RuntimeError: Event loop is closed`
- 评估指标出现NaN值

**原因**：
- RAGAS库的异步评估在某些环境下不稳定
- 网络延迟导致的超时
- API调用频率限制

**解决方案**（推荐）：
使用 `--skip-ragas` 参数跳过RAGAS评估，只使用事实检查：

```bash
python evaluate_rag.py --dataset computational --num_questions 10 --skip-ragas
```

**为什么这样做是可行的**：
- ✅ 事实检查指标通常比RAGAS更可靠
- ✅ 评估速度更快（无超时延迟）
- ✅ 对于准确性评估，事实检查已经足够
- ✅ 生产环境推荐使用

### Q1: 为什么Direct LLM的某些RAGAS指标是0？

**A**: 这是**完全正常的**！

Direct LLM模式不进行检索，所以以下3个指标恒为0：
- `faithfulness`: 无上下文可验证
- `context_precision`: 无上下文可评估
- `context_recall`: 无上下文可召回

**正确做法**: 关注`weighted_score`而非RAGAS平均分。

### Q2: 如何判断答案质量好坏？

**A**: 按优先级查看：

1. **首先看`critical_errors`**: 
   - 如果>0，说明有关键错误，答案不可信
   
2. **然后看`factual_correctness`**:
   - >0.8: 事实准确，可信度高
   - 0.5-0.8: 基本准确，有小问题
   - <0.5: 事实问题严重

3. **最后看`weighted_score`**:
   - 这是综合评分，推荐使用

### Q3: 不同模式怎么对比？

**A**: 分组对比

**答案质量对比**（所有模式适用）：
- answer_relevancy
- answer_correctness
- answer_similarity
- **weighted_score**（推荐）

**检索质量对比**（仅Agentic模式）：
- faithfulness
- context_precision
- context_recall

### Q4: 事实正确性是如何验证的？

**A**: 采用**双重验证**机制

1. **标准答案验证**: 与ground truth对比
2. **上下文验证**: 与检索内容对比

如果两者都不支持某个声明，判定为事实错误。

### Q5: 什么是"一票否决"机制？

**A**: 关键事实错误的惩罚机制

```python
if critical_errors:
    max_score = 0.3 - (len(critical_errors) × 0.1)
    # 即使表述完美，最高只能得0.3分
```

**目的**: 确保事实错误的答案不会因为措辞优美而得高分。

### Q6: 如何选择合适的数据集？

**A**: 根据评估目的选择

**场景1: 快速测试系统功能**
- 使用 `computational` (67题)
- 命令: `python evaluate_rag.py --dataset computational --num_questions 5`

**场景2: 专注某个领域评估**
- 选择相关分类，如 `materials`, `performance` 等
- 命令: `python evaluate_rag.py --dataset materials --num_questions 20`

**场景3: 全面跨领域评估**
- 使用 `all` (2644题)
- 命令: `python evaluate_rag.py --dataset all --num_questions 100`
- ⚠️ 注意：不要同时评估 `all` 和单个分类进行对比（有重复）

### Q10: 如何重新评估已有结果（不重新生成答案）？

**A**: 使用`re_evaluate.py`脚本

**使用场景**：
- 修改了评估指标的计算方法
- RAGAS评估失败需要重试
- 想添加新的评估指标
- 节省重新生成答案的时间和成本

**命令示例**：
```bash
# 重新评估单个结果
python re_evaluate.py --dataset computational --mode direct_llm

# 只重新计算RAGAS指标
python re_evaluate.py --dataset all --mode agentic_no_kg --skip-fact

# 只重新计算事实正确性指标
python re_evaluate.py --dataset all --mode agentic_no_kg --skip-ragas

# 批量重新评估所有已有结果
./re_evaluate_all.sh
```

**优势**：
- 不需要重新调用LLM生成答案
- 大幅节省时间（从小时级降到分钟级）
- 节省API成本
- 可以选择性地只重新计算某些指标

**注意**：
- 重新评估会更新原有的results.json文件
- 原始生成的答案不会改变
- 只更新评估指标

### Q11: 增量评估和批量模式有什么区别？⭐新功能

**A**: 增量评估是新增的默认模式，提供更好的容错性

| 特性 | 增量评估（默认） | 批量模式（--no-incremental） |
|------|-----------------|----------------------------|
| **保存时机** | 每完成一题立即保存 | 全部完成后保存 |
| **断点续传** | ✅ 支持 --resume | ❌ 不支持 |
| **进度丢失风险** | ❌ 无风险 | ⚠️ 中断则丢失全部 |
| **实时查看** | ✅ 可以 | ❌ 需等待全部完成 |
| **NaN重试** | ✅ 自动重试3次 | ❌ 无重试 |
| **日志详细度** | ✅ 每题详细日志 | ⚠️ 简略日志 |

**推荐使用增量评估**（默认模式）

### Q12: 中途中断了怎么办？

**A**: 使用`--resume`参数继续

```bash
# 开始评估50题
python evaluate_rag.py --dataset computational --num_questions 50

# 假设在第30题时中断（网络、API限额等）
# 已完成的30题结果已保存在results.json中

# 使用 --resume 继续（会跳过前30题）
python evaluate_rag.py --dataset computational --num_questions 50 --resume

# 系统会输出：
# 📂 Found existing progress: 30 questions already completed
# Resuming from question 31...
```

**工作原理**：
1. 系统检查results.json文件
2. 读取已完成的question_id列表
3. 跳过已完成的问题
4. 从下一题继续评估

### Q13: 为什么有些指标显示null/None？

**A**: 这通常是由于RAGAS评估返回NaN导致

**原因**：
- `answer_relevancy`最容易出现NaN（RAGAS内部问题）
- 答案过长（>2000 tokens）时更容易发生
- API限流或超时也可能导致
- RAGAS库本身的稳定性问题

**增量评估的处理**：
1. 检测到NaN自动重试（最多3次，间隔2秒）
2. 多次重试后仍失败，标记为null
3. null值不参与平均分计算
4. 不影响其他指标的评估

**如何查看NaN问题**：
```bash
# 查看某个结果中的null指标
cat results/computational/direct_llm/results.json | jq '.qa_results[] | select(.ragas_scores.answer_relevancy == null)'

# 统计有多少题有null指标
cat results/computational/direct_llm/results.json | jq '[.qa_results[].ragas_scores.answer_relevancy] | map(select(. == null)) | length'
```

**优化建议**：
- 使用更短的答案（调整max_tokens）
- 增加重试间隔（修改retry_delay）
- 检查API限流设置

## 技术说明

### 为什么事实正确性权重高？

**问题**: RAGAS过于关注表述质量

```
错误案例：
答案A: "PyDI有更好的平面性"（事实对，表述简单）
  → RAGAS: 0.65（因简单被扣分）

答案B: "PyDI展现卓越的分子构型..."（事实错，措辞华丽）
  → RAGAS: 0.85（因华丽得高分）
```

**解决**: 加权评分，事实优先

```
答案A: 0.65×0.3 + 0.95×0.7 = 0.86 ✅
答案B: 0.85×0.3 + 0.20×0.7 = 0.40 ✅
```

### 英文Prompt的优势

所有事实检查的Prompt使用英文，因为：
1. LLM在英文prompt上表现更好
2. 技术领域文献多为英文
3. 问题和答案本身就是英文
